# Shiplog 0.2.0 — Design

Builds on 0.1.1. Everything here came out of wiring Shiplog into Trackberry and syncing its real repositories on 2026-10-26.

## Goals

1. **Product-updates navigation:** the roadmap and changelog link to each other through a switcher, and hosts can add their own entries (e.g. Trackberry's News).
2. **A better default roadmap:** what Trackberry built through partial overrides becomes the gem's default, configurable for any host.
3. **No duplicate changelog entries for gems:** a change made in a gem the host depends on appears once, dated when the host upgraded.
4. **Roadmap copy that reads less like a template:** varied openings, shorter bodies.

Out of scope: hand-written news or announcement posts in Shiplog (hosts link their own news instead), a weekly digest of small changes, and the Devise redirect loop on engine mounts (a host issue).

## 1. Switcher

- The default `shiplog/_page_header` renders a switcher under the lede: Roadmap, Changelog, then `config.extra_pages`.
- `config.extra_pages = [ { label: "News", path: "/learn/news" } ]`.
  - `label` is a String, or a callable evaluated in the view (for I18n).
  - `path` is a String, or a callable evaluated in the view (for route helpers, e.g. `-> { main_app.news_index_path }`).
  - Validated at boot: an Array of Hashes with exactly those keys.
- The current page gets `aria-current="page"`, matched on `request.path` (an extra page is current when the path starts with its path).
- Host pages can render the same switcher: `Shiplog::SwitcherHelper#shiplog_switcher`, which a host adds with `helper Shiplog::SwitcherHelper`. It renders the `shiplog/switcher` partial, using only engine route proxies and no engine-only helpers, so it works in main-app views.
- New class keys: `switcher`, `switcher_link` (modifier `current`). Trackberry's Tailwind classes move from its `_page_header` override into `config.classes`.

## 2. Roadmap defaults

These move from Trackberry's overrides into the gem, with plain-CSS defaults and class keys:

- **Column status:** a rule and marker per column. Modifiers `in_progress`, `coming_soon` and `later` already exist on `column`. New keys: `column_marker`, `column_rule` (or the rule applied via the column modifier, whichever keeps markup simplest).
- **Card meta:** `card_meta`, `card_tag`.
  - Tag: the label of the subject's repository, from `config.repository_labels = { "Trackberry/iOS" => "iPhone & iPad" }`. Labels can also be callables.
  - Parts: "Includes N parts" when the issue has more than one sub-issue (I18n `shiplog.roadmap.parts` with plural forms).
- **Recently shipped:** a section after the columns.
  - It lists the last `config.roadmap_shipped_count` (default 4; 0 hides it) approved feature and change entries.
  - Each links to its month anchor on the changelog, plus a "See the full changelog" link.
  - Keys: `shipped`, `shipped_title`, `shipped_list`, `shipped_item`, `shipped_link`.
- **Footnote:** an optional `shiplog.roadmap.footnote` (empty by default, so nothing renders) and `config.feedback_path` (String or callable; omitted when nil) for the "Suggest a feature" link.
- **Caching:** the public ETag includes `Entry.approved.maximum(:updated_at)`, because the roadmap now shows changelog entries.
- **Queries:** the roadmap preloads `subject: [:repository, :children]`, keeping the page query-bounded (with a test).
- Trackberry's overrides of `roadmaps/show`, `_column`, `_card` and the switcher part of `_page_header` can then be deleted in favour of config.

## 3. Gem upgrades as the single changelog entry

### Configuration

`config.repositories` accepts per-repo options:

```ruby
config.repositories = [
  "Trackberry/trackberry",
  "Trackberry/iOS",
  { name: "Trackberry/market_data", changelog: false, gem: "market_data" },
  { name: "Trackberry/produce", changelog: false, gem: "trackberry-produce" },
  { name: "Trackberry/seaports", changelog: false, gem: "seaports" }
]
```

- Plain Strings keep 0.1 behaviour.
- `changelog: false`: the repo still feeds the roadmap (issues), but ScanChangesJob never drafts its PRs or commits.
- `gem:` is the gem name in the host's `Gemfile.lock`. It's needed because names differ (`trackberry-produce` lives in `Trackberry/produce`). The public `holidays` gem on RubyGems is **not** `Trackberry/holidays`, so name matching alone is wrong.

### Detecting an upgrade

For each merged PR in a repo with `changelog: true` (the host app):

1. Read `Gemfile.lock` at the PR's base and merge commits, using GraphQL `repository.object(expression: "<oid>:Gemfile.lock") { ... on Blob { text } }`.
   - Skip if unchanged.
   - Only for PRs whose `files` include `Gemfile.lock`. Fetch that with `pullRequest.files(first: 100) { nodes { path } }`, already in the PR query.
2. Parse both with `Bundler::LockfileParser`, and find tracked gems whose version or git revision changed.
3. For each changed gem, resolve both refs in the gem's repo:
   - a git source uses the `revision`;
   - a version tries tag `v<version>`, then `<version>` (seaports tags `v1.2.0`, market_data tags `0.2.4`).
4. List the gem repo's PRs merged between the two refs, with REST `GET /repos/{o}/{r}/compare/{old}...{new}`, then the associated PRs of those commits (GraphQL `associatedPullRequests`). Cap at 50.
5. Store the result on the host PR: a new `shiplog_pull_request_upgrades` table with `pull_request_id`, `gem_name`, `from_ref`, `to_ref`, `gem_repository`, and `changes` (jsonb list of `{number, title, body_excerpt, url}`).

### Drafting

- An upgrade PR gets **one** change draft, dated at its merge, which is when customers get it. The upgrade's change titles and excerpts go into the rewrite prompt's `<source>` context, framed as "this update includes the following changes to <gem>". The AI writes one customer-facing entry.
- A Dependabot upgrade of a tracked gem is drafted too, even though bot authors are normally excluded, because it is how customers receive the gem's changes. That's only when the upgrade has customer-facing changes; the rewriter can still mark it not customer-facing.
- The bump PR's own conventional type (`chore(deps):`) doesn't exclude it when it carries a tracked upgrade.

### Edge cases

- **No refs:** the tag isn't found, or the repo isn't accessible. Record the upgrade with an empty change list and let the rewriter work from the PR alone. Log a warning.
- **Downgrades or multi-gem PRs:** each gem is handled separately in the prompt context.
- **Lockfile path:** `Gemfile.lock` only, configurable with `config.lockfile_path` for monorepos. Other ecosystems are out of scope.

## 4. Roadmap copy

Prompt changes for the `roadmap` kind:

- Body of at most 2 short sentences, about 220 characters, enforced after parsing by truncating at a sentence boundary.
- Vary the opening. Don't start with "We're working on"/"We are working on", because the column already says so. Lead with the customer outcome ("You'll be able to…", "See…", "Send…").
- Existing rules (future tense, no unbuilt specifics, `<source>` delimiting) stay.

## Release

- **Version:** 0.2.0. These are new features. Config stays backward-compatible: Strings in `repositories` still work, and every new key has a default.
- **Upgrade notes** in the CHANGELOG: new class keys, and the switcher in the default page header. Hosts overriding `_page_header` keep theirs; Trackberry can then delete its overrides.
